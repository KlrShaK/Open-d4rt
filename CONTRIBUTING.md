# Commit Conventions

Use Conventional Commits with this project's syntax:

```txt
[type]scope: descriptive and atomic commit message
```

Examples:

```txt
[feat]src: add rotation-invariant loss term to the training objective
[fix]train: correct checkpoint-resume epoch counter
[refactor]src: isolate camera-pose recovery from the eval loop
[chore]build: add pyproject.toml so src/ is pip-installable
[docs]docs: document the WorldTrack data schema
[test]src: add checkpoint round-trip coverage
[viz]docs: tighten quantitative-results table spacing in README
```

## Types

- `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `build`, `perf` —
  standard meanings.
- `data` — adding or changing tracked datasets, fixtures, annotations, or
  taxonomy/census artifacts (not code that produces them).
- `eval` — recording the output of a benchmark run, probe, or experiment
  (result JSON/HTML, comparison reports, run logs meant to be kept).
- `viz` — changes to visualization, plotting, or reporting code (plots,
  HTML/console reports, notebook display cells) that don't alter any
  methodology, metric, or result. Use `feat`/`fix`/`refactor` instead if
  the change touches how a number is computed, not just how it's shown.

Don't invent further types. If a change doesn't fit one of these, it's
usually a sign the commit should be split.

## Scope

`scope` names the pipeline stage, module, or subsystem touched — not a
vague area. Use the directory or component name directly where possible:

- `src` / `train` — core model and training code (`src/`, `train.py`,
  `infer_track_3d.py`, `eval_track3d_in_worldtrack.py`, `configs/`)
- `docs` — `docs/` and top-level READMEs
- `build` — packaging, dependency/environment specs (`pyproject.toml`,
  `environment.yml`, `requirements.txt`)

(The agent project that used to live at `d4rt_agent/` has moved to its own
repo, `shak-spatial-agent`, with its own `CONTRIBUTING.md` and scope list
— `d4rt-agent`, `agent-v4`, `dsi-bench`, `grounding`, `prompts`, `traj3d`,
`exploration`, `notebook`, `slurm` no longer apply here.)

The message after the colon states the exact change in a short, specific
phrase — not a restatement of the scope.

## Rules

- Keep each commit atomic and scoped to one responsibility: one pipeline
  stage, one script, one benchmark step, one launcher, one notebook
  section. Don't land a trajectory-geometry change and a SLURM launcher
  tweak in the same commit just because you touched both today.
- As a rule of thumb, don't commit more than ~150–200 changed lines at
  once, unless the change is mechanical (bulk taxonomy/data ingestion,
  regenerated lockfile, notebook output re-execution) and cannot be split
  safely — if so, say so in the body.
- Don't mix unrelated concerns: commit notebook exploration separately
  from the library code it exercises, commit dataset/taxonomy additions
  (`[data]`) separately from the code that consumes them (`[feat]`/`[fix]`),
  and commit recorded benchmark results (`[eval]`) separately from the
  benchmark code that produced them.
- Commit dependency/environment changes (`environment.yml`,
  `requirements.txt`), SLURM/launcher plumbing, and formatting-only
  changes separately from feature or pipeline logic.
- Large generated artifacts (`checkpoints/**/*.ckpt`, `data/`, `demo/`,
  `logs/`, downloaded datasets) are gitignored — don't force-add them.
- Never include agent attribution in commit messages (no "generated by
  Claude", "made with Codex", or similar).
